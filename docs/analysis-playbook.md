# Analysis Playbook — `prs-troughput`

This is the **methodology contract** for any agent producing insights from this data layer. It's prescriptive: follow it, don't improvise. Improvisation is how you silently drop the 5th-most-active contributor (true story — see `output/stress-test-2026-05-08/OBSERVATIONS.md` finding #6).

> If you're an agent: read `data-contract.md` first for schema, then this for methodology, then run `views/setup.sql` + `views/contributors.sql` before any query.

## §0 The four lenses

Every leadership-relevant question maps to one of four lenses. Pick the lens, then the view.

| Lens | Question shape | Primary views |
|---|---|---|
| **Velocity** | "How fast is the team shipping?" | `kinetics_weekly`, `intensity_weekly`, `punchcard.sql`, `weekday_rollup.sql` |
| **Quality** | "Is the team trading speed for risk?" | `direct_main_risk`, `review_queue`, `refactoring_activity` |
| **Lifecycle** | "Where do changes get stuck, what's hidden?" | `invisible_wip`, `traceability`, `untraced_units`, `pr_lifecycle` (TBD) |
| **Agentic engineering** | "How is AI-assisted work showing up?" | `work_attribution_macro.sql`, filter to `agent_tooling` |

Always state which lens you're operating in when reporting.

## §1 The macro work taxonomy

Every commit / PR / branch is exactly one of these macro categories. **Do not invent new ones.** If something doesn't fit, label it `unclassified` and report it for taxonomy review.

| Category | Strategic / Operational | What it is |
|---|---|---|
| `feature_development` | strategic | New capability — `feat:` commits, `feat/*` branches, new src/ files |
| `refactoring` | strategic | Restructure without behavior change — `refactor:`, `perf:`, "extract" / "rename" / "move" verbs |
| `testing` | strategic | Test code — `test:`, `*.test.*` paths, fixtures |
| `bug_fix` | strategic | Behavior correction — `fix:`, `hotfix/*` branches |
| `agent_tooling` | strategic | AI-tooling work — `.claude/`, `.opencode/`, `claude/...` branches, `Co-authored-by: Claude` footers |
| `docs` | strategic | Knowledge artifacts — `docs:`, README/`*.md`-only changes |
| `infra_deploy` | operational | Deployment plumbing — `chore(release):`, `version updated in values-*.yaml`, Dockerfile, `.github/workflows` |
| `integration` | operational | Git plumbing — `Merge branch ...`, `Merge pull request ...`, `Revert ...` |
| `maintenance` | operational | Chore — `chore:`, lockfile bumps, dependency updates |
| `unclassified` | — | Reserved for inputs the cascade can't resolve. Should be <5%. |

The strategic / operational split matters: when you report contributor mix, **always report the strategic-vs-operational ratio**. Authors with a high operational % are doing real work, but it's a different kind of work than authors with high strategic %. Flag the ratio without judgment — the leader decides what's appropriate per role.

## §2 The 6-signal attribution cascade

When you need to assign a single macro category to a commit, run signals in this priority order. **Highest-confidence signal that fires wins.** Lower-confidence signals attach as evidence but don't override.

| # | Signal | Source | Weight | Coverage (coto-joy reference) |
|---|---|---|---|---|
| 1 | Subject noise regex | `subject` matches `Merge branch`, `Merge pull request`, `Revert `, `version updated in values-*`, `chore(release):` | **0.95** | 36% |
| 2 | Conventional Commits | `conventional_type` ∈ {feat, fix, refactor, test, docs, perf, chore, ci, build, revert} → mapped via §1 | **0.90** | 32% |
| 3 | Branch pattern | `commit_links → branches` join, branch name starts with `feat/`, `fix/`, `refactor/`, `claude/`, `codex/`, `cursor/`, `PRD-`, `qa`, etc. | **0.70** | 84% |
| 4 | Embedding label | `semantic_categories_latest` where `source='embedding'`, work-type subset, `score > 0.5` | **0.60** | 46% |
| 5 | Body footer | `body` contains `Co-authored-by: Claude`, `Generated by Claude`, `🤖 Generated`, `noreply@anthropic` → `agent_tooling` | **0.55** | 2% |
| 6 | Path heuristic | `top_level_dirs` matches `tests/`, `.github/`, `.claude/`, `docs/`, lockfile-only, etc. | **0.40** | 98% (fallback) |

**Pre-baked**: `views/work_attribution_macro.sql` implements this cascade in DuckDB. **Do not re-implement.** If you need to extend it (e.g. new noise pattern), edit the view file and bump its version comment, don't fork it inline.

When reporting attributed commits, **always include the confidence**:
- ≥ 0.90 → high confidence, report as fact
- 0.70–0.90 → medium, report with caveat
- < 0.70 → **flag for human review**; do not headline

## §3 The contributor archetypes

When summarizing a person's work over a window, classify them as exactly one of these archetypes. Use these labels verbatim — not paraphrases.

| Archetype | Signature pattern | Reference example |
|---|---|---|
| **pure_builder** | ≥50% feature_development, near-zero integration, near-zero infra_deploy | barathkumarravi on coto-joy: 19 features, 0 integration, high median churn |
| **caretaker_owner** | Diverse mix spanning ≥4 strategic categories (bug_fix + docs + testing + refactoring + features), low total volume, low churn-per-commit | Zeebee on coto-joy: 12 bug_fix + 8 docs + 6 testing + 5 features + 3 refactoring + 2 agent_tooling |
| **tactical_integrator** | High volume but ≥40% combined integration + infra_deploy, small per-commit churn | aviraj-coto on coto-joy: 464 commits, 157 integration + 90 deploys, 49-line median churn |
| **bug_fix_specialist** | bug_fix is the #1 macro category by commit count | reyuuji28 on coto-joy: 28 bug_fix commits, leading category |
| **quality_ops** | testing + bug_fix + infra_deploy together exceed feature_development | srikar-samudrala on coto-joy: 13 bug_fix + 11 infra_deploy + 1 testing > 2 features |
| **agent_collaborator** | ≥10% commits in agent_tooling OR ≥1 commit on `claude/` `codex/` `cursor/` branch | Marker, not exclusive — combine with primary archetype |
| **insufficient_data** | <10 commits in window | Don't archetype |

**These are descriptive, not normative.** A `tactical_integrator` is doing real work — release engineering, integration, deployment — that the team needs. A `caretaker_owner` may have low velocity numbers but holds the codebase together. The archetype tells the *shape*; the leader decides what shape each role should have.

### Tolerance bands and tie-breaking

The thresholds above are **defaults, not strict cutoffs**. Real contributors land near boundaries (e.g. barathkumarravi on coto-joy is 45% features with zero integration — spirit clearly `pure_builder`, fails the literal 50% rule). Apply this tie-break order:

1. **Within 10 percentage points of a threshold** → check the corroborating signals listed in the archetype row. If they fire, assign the archetype.
2. **Multiple archetypes within tolerance** → prefer the one with more corroborating signals. Document the alternative in your report.
3. **No archetype fits even with tolerance** → label `mixed`, describe the actual mix, and propose a new archetype for playbook review.

Always show your work: "Classified as `pure_builder` — features 45% (within tolerance of 50% threshold), zero integration corroborates."

## §4 Hidden work — the invisible WIP test

Whenever doing a velocity or attribution analysis, **also run `invisible_wip`**. The most leadership-relevant insight is often "this branch has 500 commits ahead of master and hasn't been touched in 32 days" — not "person X shipped Y commits this week."

Default thresholds for flagging an invisible-WIP branch:
- `ahead_main >= 50` AND `idle_days >= 14` → high concern
- `ahead_main >= 10` AND `idle_days >= 30` → medium concern
- has `task_id` AND `idle_days >= 7` → flag (a real ticket may have stalled)

## §5 Volume vs impact — the trap

**Commit count is a vanity metric.** Always pair it with at least one impact signal:
- Median churn per commit
- Distinct files touched
- Macro category mix (high integration % deflates raw count)
- Authored vs noise ratio (after stripping merges + deploy bumps)

The minimum honest table for "how is contributor X doing?" includes: total commits, **authored commits** (after `views/work_attribution_macro.sql`), strategic %, median churn per authored commit, primary archetype.

Never headline raw commit count without context.

## §6 Off-hours work — burnout signal

`views/off_hours_work.sql` returns per-author per-week percentage of commits authored outside business hours (default: weekends + before 8am + after 7pm in author-local time).

Reporting rules:
- Single-week spikes (one author, one week >40% off-hours) → context likely (release crunch, time zone shift); note but don't escalate
- Sustained ≥3-week trend ≥30% off-hours → **escalate**: this is the burnout signal
- ≥50% off-hours sustained → escalate immediately

Do not name individuals in any auto-generated report. Always frame as "team members showing pattern" + invite a 1:1 conversation.

## §7 Traceability — when to care, when not to

Traceability gaps (commits/PRs without `task_id`) are interpreted differently per archetype:

| Archetype | Untraced is... |
|---|---|
| `pure_builder` | a process gap — they should be linking work |
| `caretaker_owner` | often expected — owners ship from intent, not tickets |
| `tactical_integrator` | structural — merges and deploys don't carry ticket IDs |
| `bug_fix_specialist` | mixed — hotfixes often skip tickets; planned bug work shouldn't |
| `quality_ops` | usually fine — deploy/maintenance work is cron, not ticketed |

Always state the archetype interpretation alongside the raw % when reporting traceability.

## §8 Required reporting hygiene

Every analysis output produced by an agent MUST include:

1. **Window**: which `days_back` was used.
2. **Source view(s)**: which view filenames were the basis.
3. **Identity normalization**: confirm `views/contributors.sql` was applied.
4. **Confidence threshold**: any attribution < 0.7 is flagged.
5. **Archetype labels**: from §3 only, no invented ones.
6. **Lens**: which of the four lenses (§0) the analysis is operating in.

Templates: see `views/README.md`.

## §9 Anti-patterns to avoid

- ❌ `LIMIT N` on contributor lists without justifying why others were dropped (use `views/active_contributors.sql` instead).
- ❌ Inline `CASE WHEN lower(author_name) IN (...)` (use `views/contributors.sql`).
- ❌ Naïve `read_parquet('output/ledger/**/*.parquet')` without dedup (use `*_latest` views or `views/setup.sql`).
- ❌ Inventing new macro categories (extend §1 or use `unclassified`).
- ❌ Reporting commit count alone (always pair with impact — see §5).
- ❌ Naming individuals in burnout-signal reports (frame as patterns).
- ❌ Treating high-confidence and low-confidence attributions equally (§2 thresholds).
